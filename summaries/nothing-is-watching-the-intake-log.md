What was built: The dispatcher remembers what went wrong on each tick. The same failure ten ticks in a row, about ten minutes, is treated as a broken machine and reported once. If every failure is about one task, that task is marked blocked with the error as its note. Otherwise the log gets a NEEDS YOU line and the laptop gets the same desktop notification the queue alarm already uses. A clean tick resets the count, and a different failure starts a new one.
Choices: Ten ticks, set by INTAKE_ALARM_AFTER, so a bad minute or a blip on the network says nothing. One alarm per failure, never one per tick. Running unmerged code because main's scripts are broken counts as a failure, because that is the twelve hours this request was about: the fallback kept the queue alive and nobody read the log.
Liberties: task-status.mjs used to log a caught error and exit 0, so a broken tick looked like a quiet one. It exits 1 now. inbox.mjs and task-status.mjs take MTG_API_BASE, so tests can point them at a Worker that is not there instead of production.
